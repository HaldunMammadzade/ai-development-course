# Database

PostgreSQL 16 via Prisma 7. The identity migration created `users`, `sessions`, `email_verification_tokens`, and `password_reset_tokens`. The learning migration adds the Phase 1 curriculum, progress, teaching, memory, and plan tables, and drops the interim `quotas` table. Prisma 7 reads the connection URL from `packages/database/prisma.config.ts`, not from the schema. The client is generated into `packages/database/src/generated`, and that directory stays out of git.

Phase 2 and later product tables are created as each step lands. Organizations are still not created. `admin_audit_log` and `users.role` are created by the admin analytics migration. Step 10 created a smaller `exercises` and `exercise_attempts` pair for authored checks. Those rows do not store solution code, tests, or files.

Conventions:

- Primary keys are UUIDs generated by the database.
- Timestamps are `timestamptz`, stored in UTC.
- Tables and columns use `snake_case`. Prisma models use singular PascalCase mapped to these tables.
- Student-owned rows include `user_id` and are indexed from that column.
- Deletes of a user cascade through student data. Curriculum rows are not owned by a user.
- Money and token cost use integers. Cost is USD micros (`cost_micros`). Prices are minor units plus a currency code.
- JSONB is for lesson block bodies, model payloads, and event metadata. Anything queried in a filter becomes a real column.

Unseen skill and zero skill are different. Absence of a `skill_mastery` row means the concept has no evidence. The score `0` is not used as a default.

## Authored exercises (step 10)

`exercises`: id, slug unique, lesson_id, concept_id, title, prompt, instructions, type (`multiple_choice` or `code_text`), language null, difficulty, position unique per lesson, starter_code null, rules jsonb, options jsonb, published, timestamps. Rule points live inside `rules`, not in a separate column.

`exercise_attempts`: id, exercise_id, user_id, client_attempt_id, submission, status (`passed` or `failed`), score 0–100, passed, feedback, passed_rules jsonb, failed_rules jsonb, attempt_number, created_at. Unique on `(user_id, exercise_id, client_attempt_id)`.

Rules are declarative JSON. They are not executable code. A passing attempt also inserts `learning_events.source = exercise` with `source_id` set to the attempt id.

## Phase 2 tables

Not created. The step 10 tables above are not this schema. Created with the runner milestone, not before.

**exercises**: id, slug unique, concept_id, lesson_id null, title, prompt, difficulty, objective, starter_code, estimated_minutes, solution_code, solution_explanation, status, created_by (`author` or `model`), review_status (`approved`, `pending`).

**exercise_hints**: exercise_id, position, body. Served in order before any model hint.

**exercise_tests**: exercise_id, visibility (`visible` or `hidden`), name, code. Hidden tests never go to the client or the model context of a hint.

**exercise_attempts**: id, user_id, exercise_id, session_id null, started_at, submitted_at, status (`running`, `passed`, `failed`, `error`), hint_count, duration_ms.

**attempt_files**: attempt_id, path, content. MVP is a single `main.ts` or `main.jsx` file. The table still uses a path so multi-file projects do not require a new submission shape.

**test_results**: attempt_id, test_id, passed, message. Hidden test messages returned to the student are generic. Full assertion output stays server-side.

**code_reviews**: attempt_id unique, overall smallint, dimensions jsonb, speech text, model, created_at. Dimensions are the fixed set: correctness, readability, architecture, performance, security, plus typescript, react, accessibility, and testing when the exercise declares them.

The model does not receive `solution_code` during a hint. Evaluation after tests passes may receive it so feedback can compare approaches. That prompt is a different task from hinting.

## Phase 3 tables

**projects**, **project_milestones**, **project_tasks**, **task_attempts**, **task_reviews**.

A task has a status (`todo`, `doing`, `review`, `done`), a parent task id for subtasks, and a position. The student submits an attempt. The mentor writes a review. The project generator may draft tasks, and a published flag keeps drafts away from the student until the Phase 3 review step exists. Until then, seeded projects are authored in git the same way lessons are.

## Phase 4 tables

**interview_sessions**: user_id, kind (`junior_frontend` through `senior_backend`, plus `fullstack`), state, started_at, ended_at.

**interview_turns**: session_id, role, speech, payload.

**interview_scores**: session_id unique, overall, technical, problem_solving, communication, code_quality, system_design, plan text.

Voice does not add tables. A voice turn is a teaching message with `metadata.channel = voice` on the learning event or a `channel` column on `teaching_messages` added in that migration (`text` default, `voice` optional).

## Billing tables (step 17)

**plan_prices**: slug unique, plan_code, currency, amount_minor, billing_interval, provider_price_id unique when set, active. No card data.

**payment_customers**: one row per user, provider, provider_customer_id. A provider reference, not a card.

**subscriptions**: one row per user. Provider subscription id, price, status, period, cancel_at_period_end, scheduled_price_id, last_event_at.

**checkout_sessions**: unique (user_id, client_checkout_id). Stores the pending URL. A repeated key does not open a second provider session.

**payment_events**: unique (provider, provider_event_id). Status is processing, processed, ignored, or failed. The raw provider body is not stored.

Learning tables are not deleted when a subscription expires.

**operational_jobs**: name, idempotency key unique together, payload, status (`pending`, `processing`, `completed`, `dead`), attempts, max attempts, run_after, and an error code. Email payloads are cleared when the job completes or is dead-lettered. Cleanup deletes completed and dead rows after 7 days. It does not delete pending work.

Cleanup, run by the `maintenance` job, physically deletes only rows that are already temporary:

- sessions that are revoked or past `expires_at`
- verification and reset tokens that are consumed or expired
- student teaching messages whose payload status is still `pending` and older than 60 seconds
- exercise, project, and interview execution claims older than 2 minutes
- checkout sessions still `pending` after 24 hours
- rate-limit buckets whose window start is older than 8 days

It does not delete users, curriculum, progress, mastery, exercise attempts, project history, interview history, speaking attempts, subscriptions, or payment events. An active session is not deleted. A rate bucket inside the longest current window (7 days for interview starts) is not deleted.

## Phase 5 tables

**organizations**: id, name, kind (`school`, `university`, `training_center`, `company`).

**organization_members**: organization_id, user_id, role (`owner`, `teacher`, `student`).

**subscriptions**: user_id or organization_id, provider, provider_customer_id, provider_subscription_id, plan_code, status, period.

**billing_events**: provider event id unique, payload, processed_at. Idempotency for webhooks.

**admin_audit_log** (created): admin user id, action, optional target type and id, correlation id, created_at. No request body and no search text. Indexes: `(admin_user_id, created_at)` and `created_at`.

`users.role` is `account_role` (`user`, `admin`), default `user`. It is not accepted on register. Support, instructor, and analyst are not enum values yet.

Analytics read the existing tables. There is no event warehouse and no Redis cache. Windows are Asia/Baku calendar days: today, 7 inclusive days, or 30 inclusive days, ending at the request time. Counts use `COUNT` and `GROUP BY`. Student search pages at most 50 rows and then one grouped last-activity query for those ids.

Indexes added for those reads: `users(created_at)`, `users(email_verified_at)`, `lesson_progress(lesson_id, status)`, `lesson_progress(started_at)`, `exercise_attempts(created_at)`, `exercise_attempts(user_id, passed)`, `ai_usage(task_type, created_at)`, `transcription_usage(created_at)`, `transcription_usage(status)`, `subscriptions(status)`, `payment_events(status, received_at)`, `operational_jobs(status, updated_at)`, `daily_activity(activity_date)`.

Active students are a `UNION` of distinct user ids from `daily_activity` (Baku dates), lesson progress, exercise attempts, teaching sessions, interviews, and speaking attempts. Funnel rates are lifetime observed counts. A zero denominator is null, not zero. Lesson completion rate uses distinct students who started that published lesson. Concept averages come from `skill_mastery`. Misconception frequency groups `misconceptions.code`. AI cost is `SUM(ai_usage.cost_micros)`. Speech cost is `SUM(transcription_usage.cost_micros)`. Failed AI calls and failed transcriptions are not written, so those failure counts are not reported as zero. Payment and email/job failures come from `payment_events.status = failed` and `operational_jobs.status = dead`.

Catalog recurring amount sums `plan_prices.amount_minor` for subscriptions that still grant access. The API returns it only when a payment provider is configured, and labels it estimated catalog revenue.

## Seed plan

`packages/curriculum` contains the Frontend and Backend path outlines.

Phase 1 publishes real lessons only for Frontend Module 1 (Web Fundamentals) and Module 2 (HTML), enough to run the full session loop twice. Every other module in both paths exists as `draft` with titles and concept links, and no published blocks.

Concept slugs for the first two modules are written by hand. The mastery graph starts there and grows as lessons are published.

## Retention

- Account deletion sets `users.deleted_at`, revokes sessions, and a job hard-deletes student rows after 7 days.
- `teaching_messages` older than 180 days are summarized into `teaching_sessions.summary` if a summary is missing, then deleted. Mastery events and misconceptions remain.
- `ai_usage` is kept 18 months for cost reporting.
- `email_tokens` are deleted when used or expired.

Exports of a student's data are a Phase 5 admin/account feature. The schema does not block them: student data is keyed by `user_id`.

The cleanup job above does not implement account deletion or the 180-day message summary. Those remain future work. Do not run `prisma migrate reset` against a database that holds students.

## Backup and recovery

Postgres is the system of record. Take a physical or logical backup at least daily, and a backup immediately before `prisma migrate deploy`. Restore into an empty database, run `prisma migrate deploy` only if the backup was taken before that migration, then start the API and confirm `GET /api/v1/health/ready` returns ok. Practice a restore on a non-production server. The backup must include users, sessions, curriculum, progress, mastery, exercises, projects, interviews, speaking, subscriptions, payment events, and `ai_usage`. This repository does not ship a backup service and the docs do not contain database credentials. Store the backup outside the database host.

A local logical drill used `pg_dump --format=custom` of the development database and `pg_restore` into a new empty database. Counts matched for users, sessions, lesson progress, skill mastery, exercise attempts, project milestone progress, interview sessions, speaking attempts, subscriptions, payment events, admin audit log, and `ai_usage`. The drill databases were dropped. The development database was not reset.

The code-review migration file was later found as an empty iCloud placeholder. The bytes that had been applied were recovered from the original write. They are 1372 bytes and their SHA-256 is the checksum already recorded when that migration was applied. A rewritten copy and a local checksum edit from the first repair were both reverted. Fresh `prisma migrate deploy` and the existing development database now use that same file. No forward migration was added: the applied SQL already creates `code_review_mode`, `code_review_status`, and `code_reviews`.

## Production migration

1. Take a logical backup and confirm it can be read. Do not continue without that backup.
2. Run `prisma migrate status` against the target database. Stop if it reports a checksum mismatch, a failed migration, or a history that does not list the repository migrations in order.
3. Run `prisma migrate deploy`. Do not run `prisma migrate reset`. Do not delete rows from `_prisma_migrations`. Do not edit a migration file that has been applied.
4. Run `prisma migrate status` again and confirm there are no pending migrations.
5. Start the API and confirm `GET /api/v1/health/ready` returns ok.
6. Confirm `code_reviews`, `projects`, `interview_sessions`, `speaking_attempts`, `subscriptions`, `payment_events`, `operational_jobs`, and `admin_audit_log` exist.

Rollback of a bad release is restore of the backup into a replacement database and redeploy of the previous build. Do not roll back by deleting migration history.

If deploy reports that a migration was modified after it was applied, stop. Do not update `_prisma_migrations.checksum`. Compare the file SHA-256 with the checksum stored in that database. The canonical `20261007090000_code_reviews` file in this repository hashes to `cfc84d5261f2266ad66fff10450749fb564ada12263617892402244297308849`. A database that stores a different checksum was not migrated from this history. Inspect its schema against a fresh database created with `prisma migrate deploy` before any repair. A checksum edit is not a deployment step.
